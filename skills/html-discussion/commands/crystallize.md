You're synthesizing a discussion doc into canonical state. The user is signalling "this discussion's decisions are crystallized — make the codebase and documentation reflect them."

**Input**: `$ARGUMENTS` (the discussion doc path).

**Your job — in order:**

1. **Read the discussion doc end to end.** Identify decisions that need canonical-state reflection. Note the slug (filename without `.html`) — you'll use it for `@scope:` tagging in step 3b.

2. **Categorize each change** per your project's guidelines (e.g., augment-vs-new-commitment):
   - **Augment existing** (LLM authority — apply directly): tag flips, additional test path metadata, or status additions.
   - **New canonical** (needs user approval first): new commitments/decisions in your architecture/design files, or new testing scenarios.

3. **Augment-existing changes** — apply directly. Print a concise "Applied" list (file:line + nature of change).

   **3b. Scope tagging** — for every scenario or test this discussion touches (augmented or newly added), consider adding a `@scope:<slug>` tag to the tag line/metadata if supported by your project's conventions. This acts as the executable link between scope and code specs, enabling selective test reruns.

4. **New-canonical changes** — draft the diffs, show each in a tight summary (file path + what's being added + why one-liner). Ask the user to approve before applying. Apply on approval. Print an "Approved + applied" list.

5. **Flip manifest `draft` → `active`.** If the discussion has a sidecar JSON manifest at `docs/discussions/<slug>.json` AND its current `status` is `draft`, flip to `active` and populate `scope_owns` with the commitment/decision refs this discussion canonically owns. Use `jq` or standard json editors:
   ```sh
   jq --arg now "$(date -u +%FT%TZ)" \
      --argjson scope_owns '["DECISION-1","DECISION-2"]' \
      '.status = "active" | .updated = $now | .scope_owns = $scope_owns' \
      docs/discussions/<slug>.json > /tmp/manifest.json && mv /tmp/manifest.json docs/discussions/<slug>.json
   ```
   If the manifest is missing or status is already `active`/`shipped`, skip silently.

6. **Run any custom build/indexer scripts** (e.g., `python3 scripts/traceability/build.py` if present) to refresh indices or project dashboards.

7. **Run any validation or audit scripts the project provides** (catalog linters, doc auditors — including this skill's `scope-lint.sh` if the project uses `@scope:` tags) to confirm no doubles, orphans, or dangling references in the catalog.

8. **Report**:
   - Applied directly: <list, including tag additions>
   - Approved + applied: <list>
   - Manifest status: `draft → active` (with scope_owns count) OR `unchanged` (already active / no manifest)
   - Audit/Build verdict: PASS or FAIL with specifics
   - Suggested next step: dispatch implementation with your project's workflow (e.g., the ping-pong skill) if ready, OR `/discussion ship <slug>` if work already landed.

**Don't:**
- Don't add duplicate scenarios/tests for requirements that are already mapped — avoid creating catalog doubles.
- Don't kick off implementation yourself — the user decides when to dispatch.
- Don't manually edit auto-generated reports/receipts if they are regenerated by build/traceability scripts.
- Don't propose excessive changes without validation; focus on the high-level decisions.

**Most common cases (handle inline without ceremony):**
- "This discussion adds tests for an existing decision" → just append test references to the existing spec/scenario.
- "This discussion ships a status update on a feature already in flight" → update the status metadata in the description block.
- "This discussion is a closeout" → add a merged banner or status marker to the discussion document with the closing commit SHA.
